# HustMCL 技术选型与 MVP 项目规划

更新日期：2026-10-21。状态：M0 已动工；已有核心库、Java 运行时选择规则与离线 CTest，尚无完整启动器或性能原型验证。桌面技术栈仍需目标工具链实测。当前可执行命令见[构建与测试](构建与测试.md)。

文档分工：本文件维护产品范围与验收目标；[架构设计](架构设计.md)维护模块约束、PCL / HMCL 参考依据与 M0 实施顺序；[验证记录](验证记录.md)只记录实际执行结果。

## 0. 本轮确定的工程方向

优先级为 **可维护性 → 安装与启动可靠性 → 功能广度 → 视觉装饰**。在框架设计上参考 PCL 和 HMCL，吸收任务组织、启动能力分区和界面反馈的思路，按 HustMCL 的 C++ / Qt 路线独立设计。参考方向不改变 Windows 10 / Windows 11 x64、原版优先和校园主题定位。

可维护性通过可检查的约束落实：核心规则不依赖 UI、网络或真实文件系统；应用层统一编排任务；外部能力通过小接口替换；CMake 按目标限制依赖；测试覆盖失败与恢复场景。接口随首个用例建立，不提前搭建通用插件、通用任务图或多套后端。

协作分工：Codex 负责 core、application、基础设施、构建与集成验收；全部前端（ui、resources、后续发布界面）交由 DSH 中的 DeepSeek。交接明确文件范围、应用接口、基线命令与验收场景；每批完成并提交后再交接，避免双方修改同一文件。

官方仓库与本轮阅读范围见[架构设计第 1 节](架构设计.md#1-参考项目与采用范围)。PCL 的自定义许可与 HMCL 的 GPLv3 及附加条款需要分别核对，不能把公开源码视为可任意移植。当前没有引入两者源码、图标或主题素材。

## 1. 产品定位与约束

HustMCL 是华中科技大学主题、面向新手的 Minecraft Java Edition 通用启动器。当前没有配套服务器或整合包；长期核心体验是游戏与整合包的一键部署，后期计划接入华科 SSO。

首版仅面向 Windows 10 / Windows 11 的 x64（64 位）架构，使用 C++，强调低资源占用、简单交互和可靠启动。不支持 Windows 7、Windows 8 / 8.1、32 位 Windows 或 ARM64 原生版本。Windows 10 的最低具体构建号由最终框架版本和干净系统测试确定。

启动器、随包原生依赖和自动安装的 Java 运行时统一使用 x64；手动指定 Java 时验证架构，发现 32 位运行时则提示更换。构建与发布仅生成 x64 产物，不为旧系统维护兼容分支。

MVP 成功标准：没有 Java、没有 Minecraft 的用户，使用具备游戏授权的微软账号，通过启动器安装受支持的原版游戏并进入主菜单；再次打开时可直接启动已安装实例。

## 2. C++ UI 框架比较

以下内存评价是根据框架结构、渲染方式和所需依赖作出的工程预判，不是同条件基准测试。界面复杂度、图片尺寸、构建方式和运行时版本都可能改变结果。安装包体积、进程私有内存、工作集与 GPU 内存必须分别测量，不能相互替代。

| 方案 | 内存与资源预期 | 界面美观与定制 | 开发难度 | 对 HustMCL 的判断 |
| --- | --- | --- | --- | --- |
| Qt 6 Widgets | 中低到中等；可以不引入 QML、浏览器和持续动画，仍需 Qt DLL 与平台插件 | 默认偏传统；通过布局、样式表和少量自绘可实现简洁校园主题 | 中低；控件、网络、JSON、进程和工具链较完整 | **首选：整体平衡最好** |
| wxWidgets | 偏低的候选；尽量采用系统原生控件，具体值需实测 | 原生桌面感较强；统一品牌样式、圆角卡片等需要额外定制 | 中等；常规表单容易，深度美化成本上升 | 若更重视原生风格和轻量，可作为备选 |
| WinUI 3 + C++/WinRT | 中等的候选；需考虑 Windows App SDK、渲染及部署依赖；原生不等于占用最小 | Fluent 风格开箱即用，现代 Windows 视觉优势明显 | 中高；涉及 XAML、C++/WinRT、异步和应用部署 | 若 Windows 现代视觉优先，可选；当前不优先 |
| Qt Quick + C++ | 需额外考虑 QML 引擎、场景图与 GPU 资源；不能简单断言总比 Widgets 大 | 动画、响应式布局、自定义视觉较方便 | 中等；需掌握 QML 与 C++ 边界 | 适合更强动效需求，MVP 暂无必要 |
| FLTK | 轻量候选；小型、模块化是其设计目标 | 默认视觉朴素；现代校园主题需要较多设计与自绘 | 基础界面较容易，产品级美化与交互中高 | 适合极简工具，当前视觉与效率不够均衡 |
| 直接使用 Win32 控件 / 自绘 | 最低基础依赖的候选，但自绘与图形资源仍可能增加占用 | 普通原生控件易做；精致主题需自行实现大量细节 | 高；布局、DPI、输入、可访问性和状态管理工作多 | 不建议用首版时间换取尚未证明必要的节省 |

Qt 官方将 Widgets 定位于成熟桌面控件，将 Quick 定位于动态流畅界面：[Qt UI 技术说明](https://doc.qt.io/qt-6/topics-ui.html)。wxWidgets 的原生控件设计见[官方概览](https://wxwidgets.org/about/)。WinUI 3 属于 Windows App SDK，提供现代 Windows UI：[官方说明](https://learn.microsoft.com/en-us/windows/apps/winui)。FLTK 的小型模块化定位见[项目官网](https://www.fltk.org/)。表中适配判断与难度评级是针对本项目的推断。

Dear ImGui 不进入主界面候选：其项目定位主要面向开发工具和内容制作工具。它可以快速制作调试面板，但面向新手的桌面应用还要评估输入法、键盘操作和可访问性等细节，不能仅凭代码小或 Demo 简单决定选型。[项目说明](https://github.com/ocornut/imgui)

## 3. 推荐技术栈

推荐采用 **C++20 + Qt 6 Widgets + CMake + MSVC x64**。选用实际可获取、支持目标系统的稳定 Qt 小版本并锁定补丁版本，不在规划阶段凭空指定最新版。

| 用途 | 推荐方案 | 说明 |
| --- | --- | --- |
| UI | Qt Widgets、布局系统、少量 QSS / QPainter | 默认系统标题栏；校园静态图片、统一间距与配色；不先引入大型皮肤库 |
| 构建 | CMake + CMakePresets + MSVC | Debug / Release 配置分离；记录编译器、SDK 与依赖版本 |
| HTTP / JSON | Qt Network、QJsonDocument | 流式下载；共用网络管理对象；避免重复引入同用途库 |
| 异步任务 | Qt 网络事件机制；工作线程处理校验和解压 | UI 线程不进行阻塞磁盘或长时间计算 |
| 配置 | 带 schemaVersion 的 JSON；QSettings 仅存窗口等 UI 偏好 | 配置单一写入入口、原子保存；账号令牌不放普通配置文件 |
| 凭据 | Windows DPAPI 加密存储适当的认证数据 | 日志脱敏；退出账号清理凭据；不收集微软密码 |
| 进程 | Qt 进程能力，必要时封装 Win32 创建进程 | 参数分项传递；验证中文路径、参数转义和启动器退出后游戏存活 |
| 日志 | Qt 日志处理器 + 有大小限制的文件 | 按实例保留启动日志，隐藏 token 等敏感信息 |
| ZIP 解压 | 优先评估 miniz 等维护中的库 | 实现前检查版本和许可证；拦截目录穿越；不使用 Qt 私有 ZIP API |
| 发布 | windeployqt + 便携 ZIP 起步 | 干净 Windows 验证；按用户目录存放数据；之后增加安装器 |
| 测试 | CTest + Qt Test | 核心与用例测试无需显示窗口、真实账号或公网；另做本地 HTTP 集成与干净系统验收 |

Qt 官方提供 [windeployqt 部署工具](https://doc.qt.io/qt-6/windows-deployment.html)。计划采用动态链接；发布时核对实际模块的许可证、附带声明及适用源代码/替换要求，动态链接本身不代表自动满足所有要求：[Qt 开源许可说明](https://www.qt.io/development/open-source-lgpl-obligations)。

选择 Widgets 的理由：首版只有少量页面，没有复杂动效需求；使用同一套基础设施完成网络、JSON、进程和 UI，可以减少依赖组合与维护成本。低内存应通过资源限制和测量落实，不以“C++”或“原生”作为性能证明。

## 4. MVP 范围

### 必须完成

- 微软账号登录、授权状态检查、凭据保存、过期刷新与退出账号。使用系统浏览器或经验证的官方支持流程，不嵌入浏览器运行时。
- 原版正式版列表与明确的“已验证版本”标记；提供一个默认推荐版本。
- 从版本元数据解析游戏文件、依赖、资源、平台规则、原生库和启动参数。
- 安装进度、有限并发、失败重试、完整性校验、取消与再次安装时复用已校验文件。
- 检测 Java 的实际版本和架构；根据游戏需求选择运行时，提供手动指定入口。
- 无可用 Java 时获取适用运行时；下载来源、校验信息和分发方式在技术验证阶段确定。自动安装 Java 属于最终 MVP 验收范围。
- 每个实例隔离存档、模组预留目录、设置与日志；公共资源可缓存复用。
- 设置游戏目录与内存上限；启动前检查磁盘空间、Java 和安装完整性。
- 启动游戏，展示启动结果，提供日志入口；允许启动后关闭启动器而不结束游戏。
- 静态华科主题；适配中文、键盘操作和常见 Windows 缩放比例。

### 明确延期

Fabric / Forge / NeoForge、整合包导入与市场、华科 SSO、服务器列表、多人社区、多账号切换、快照与全部历史版本兼容、动态背景、托盘常驻、自动更新器。

首版允许展示版本列表，但不能把可见版本等同于已承诺支持的版本。以一个现代正式版打通流程，再按不同 Java 需求选择代表版本验证，形成明确兼容矩阵。Java 版本要求由受验证的元数据与必要的兼容规则决定，不为所有版本强制使用同一个 JRE。

## 5. 页面与交互

| 页面 | 核心内容 |
| --- | --- |
| 首页 | 当前账号、当前实例、准备状态、一个主操作按钮 |
| 安装游戏 | 推荐版本、其他正式版、目录、所需空间与安装状态 |
| 设置 | Java 自动选择 / 手动路径、内存、游戏目录、启动后行为 |
| 日志与错误 | 用户能理解的原因、可执行下一步、查看或导出脱敏日志 |

主按钮随状态变化：登录 → 安装 → 准备环境 → 启动。显示实际处理步骤，不伪造百分比；依赖未知时显示阶段进度。Java 安装先说明将下载的运行环境和位置，尽量减少要求新手理解的术语。

安装状态：未安装 → 解析 → 环境准备 → 下载 → 校验 → 就绪。取消和失败保留可复用内容；重试从检查缓存开始。就绪后独立管理启动中、运行中、退出和启动失败状态。

## 6. 最小架构与目录

保持单个桌面应用、清晰模块边界，不引入本地 HTTP 服务或插件框架。下面是目标目录，随首个实际用例建立，不是当前已存在的代码结构。

```text
src/
  app/         入口与依赖组装
  ui/          页面与状态展示
  application/ 安装、登录、启动用例、任务状态与外部能力接口
  core/        确定性的版本模型、规则解析、实例与计划
  services/    网络、存储、Java、账号、校验、解压与进程的实现
  platform/    基础设施内部的 Windows 凭据与平台适配
resources/     图标、主题、静态图片
tests/         单元、用例、本地集成测试与固定输入样本
docs/          规划、构建说明、兼容矩阵
```

构建依赖为 `ui → application → core`、`infrastructure → application / core`；`infrastructure` 包含 `services/` 与 `platform/`，由 `app/` 完成组装。`core` 可使用 Qt Core 的值类型与 JSON 能力，但禁止 QWidget、Qt Network、Win32 和真实 I/O；`application` 不依赖具体服务。不能仅靠目录名判断是否解耦。

界面只调用应用用例并展示状态，不直接组装启动命令、下载文件或刷新凭据。先用固定元数据与替代服务验证用例，再接真实服务和页面。安装计划表达文件需求与有限阶段，不提前实现通用任务图。具体模型、线程归属、取消与重试约定以[架构设计](架构设计.md)为准。

程序文件与可变数据分离。配置带版本号并原子写入；凭据独立保存。下载写临时文件，校验后发布至缓存；实例完整性检查完成后才提交就绪记录。MVP 对同一数据根的修改任务串行执行，持有跨进程写锁；运行中实例拒绝冲突修改。失败恢复不删除存档，解压拒绝越界路径和链接逃逸。

## 7. 性能预算与验证方法

以下数值是首轮工程目标，不是已验证成绩，也不是对候选框架的预测值：

- 发布版首页静置 30 秒后，进程 Private Bytes 目标不超过 100 MiB。
- 安装普通原版期间，启动器 Private Bytes 峰值目标不超过 200 MiB；不计游戏 JVM 和临时 Java 探测子进程，但单独记录子进程开销。
- 首页静置时平均 CPU 目标低于整机 1%；无持续刷新动画或轮询忙等。
- 指定参考机上，冷启动到可交互目标不超过 2 秒；不等待联网成功。
- 背景图片按实际显示需要缩放解码，下载流式落盘，校验/解压限制缓冲和并发，日志滚动保存。

原型测试统一使用 Release x64、相同窗口尺寸、同一背景图、版本列表和模拟下载任务。记录 Windows 版本、CPU、内存、显卡、屏幕缩放、Qt 版本和构建参数。至少重复 5 次，分别记录冷启动中位数、空闲/安装峰值 Private Bytes、Working Set、CPU、GPU 内存、发布目录与压缩包大小。Java、游戏、浏览器登录和系统缓存需分开归因。

先验证 Qt Widgets 原型。若预算超标，先定位图片、缓存、日志与组件加载；如果空壳已明显不满足要求，再制作相同内容的 wxWidgets 原型比较。没有必要同时实现六套启动器。

## 8. 里程碑与验收

| 阶段 | 交付物 | 退出条件 |
| --- | --- | --- |
| M0 技术验证 | 最小构建与离线测试入口、模块依赖约束、Widgets 原型、性能与部署记录、认证与 Java 获取验证 | 依次完成架构设计中的 M0.1–M0.4；核心测试无需 UI / 公网；干净机器可运行；预算有数据；认证链实际可用；确定运行时来源 |
| M1 启动核心 | 版本解析、Java 检测、启动计划、进程日志 | 合法认证状态下，已安装的目标版本可启动；路径与参数测试通过 |
| M2 安装闭环 | 下载、校验、解压、缓存、运行时安装 | 从空目录完成安装；取消、断网后重试不会损坏就绪实例 |
| M3 新手体验 | 登录刷新、四个最小页面、主题、错误反馈 | 无 Java、无游戏环境的用户按正常流程进入游戏主菜单 |
| M4 发布候选 | 发布包、兼容矩阵、测试记录、依赖声明、使用说明 | 在 Windows 10 / Windows 11 x64 干净环境分别完成验收；不依赖开发机 PATH 或 Qt 安装 |

不预先承诺日历工期。M0 完成后根据认证接入、版本解析和部署难度估算；可运行的小交付比仅按日期划分更可靠。

每阶段除了用户可见结果，还必须满足维护验收：依赖方向无倒置、业务规则只保留一份、失败原因有稳定错误码、受影响的测试可重复执行、文档状态与实际实现一致。不得用增加抽象层或文件数量代替这些结果。

## 9. 关键测试与风险

| 项目 | 验证内容 / 处理方式 |
| --- | --- |
| 认证接入 | 尽早验证客户端注册、授权链、游戏所有权检查与刷新；不把取得普通微软 token 等同于可启动 Minecraft |
| Java 兼容 | 错误版本、错误架构、路径含空格、中文路径、失效手动路径、机器未装 Java |
| 下载可靠性 | 断网、超时、限流、校验失败、磁盘不足、取消、重复安装、临时文件清理 |
| 文件与进程 | 解压路径穿越、目录无写权限、参数转义、启动器关闭后游戏存活 |
| 实例隔离 | 不同实例存档和设置不覆盖；更新不删除用户存档 |
| UI | 100% / 150% / 200% 缩放、长中文路径、键盘焦点、后台任务不冻结界面 |
| 分发 | 无开发依赖机器、缺少运行库、普通用户权限、完整部署文件清单 |

账号和 Java 获取都是早期技术风险，需要在 M0 查阅对应最新官方资料并实测。本规划没有宣称这些外部接入已经完成或保证无需审批。若存在接入障碍，应调整里程碑，不以伪登录或未完成环境配置的界面冒充 MVP。

## 10. MVP 后续路线

1. 增加一个加载器及一种整合包格式，沿用安装计划、缓存和完整性校验，实现第一版整合包一键部署。
2. 根据真实用户反馈完善推荐整合包和下载体验，再考虑内容服务。
3. 华科 SSO 作为独立校园身份接入，用于校园内容与活动；Minecraft 游戏授权与校园身份分开管理。
4. 有明确需求后再加入自动更新、多账号与更广泛版本兼容。
